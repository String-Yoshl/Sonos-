## セキュリティ所見

### S1（高）全 API が無認証

- **場所**: `webapp.py`（全 `/api/*` ルート）
- **問題**: 認証が一切なく、同一 LAN 上の任意の端末（来客のスマホ、侵害された IoT 機器等）が
  スケジュールの閲覧・作成・削除・即時再生・設定変更を実行できた。
  `serve` は既定で `0.0.0.0`（LAN 全体）に公開されるため影響が広い。
- **修正**: `auth.py` を新設。初回起動時に `secrets.token_hex(16)` でトークンを生成し
  `data/auth_token`（パーミッション 0600）に保存・再利用。`/api/*` は
  `X-Auth-Token` ヘッダまたは `Authorization: Bearer` を必須とし、
  `hmac.compare_digest`（定数時間比較）で照合。UI シェル（秘密を含まない静的ファイル）は
  認証不要のまま。クライアントは起動 URL の `?token=` を localStorage に保存して
  URL から除去し、401 時は再入力を促す。
- **修正後の挙動（テストで担保）**:
  - トークンなし → `401`（GET/POST/DELETE すべて）
  - 誤トークン → `401`、正トークン（ヘッダ/Bearer）→ `200`

### S2（中）セキュリティヘッダ皆無・インラインスクリプト

- **場所**: `webapp.py`（レスポンス全般）、`static/index.html`（インライン `<script>`）
- **問題**: CSP がなく、将来 XSS が混入した場合の緩和層がゼロ。クリックジャッキング
  （iframe 埋め込み）や MIME スニッフィングへの防御もなかった。
  index.html のインライン SW 登録スクリプトが厳格 CSP の導入を妨げていた。
- **修正**: 全レスポンスに
  `Content-Security-Policy: default-src 'self'; img-src 'self' data:; base-uri 'none'; frame-ancestors 'none'`、
  `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy: no-referrer`
  を付与。インラインスクリプトは `app.js` 冒頭へ移動し、`<script>`（インライン）を排除。

### S3（低）URI 音源のスキーム未検証

- **場所**: `models.py` `Source.validate`
- **問題**: `uri` タイプの音源に `javascript:` / `file:` / `data:` 等の無意味・危険な
  スキームを保存できた（UI 表示はエスケープ済みのため即時の XSS はないが、
  多層防御として不適切な値は入口で拒否すべき）。
- **修正**: `urllib.parse.urlsplit` でスキームを取り出し、スキーム無しおよび
  `javascript/data/file/vbscript/about/blob` を拒否。Sonos 独自スキーム
  （`x-rincon-*` 等）を許容するため拒否リスト方式を採用。

### S4（低）API レスポンスのキャッシュ抑止なし

- **場所**: `webapp.py`
- **問題**: `/api/*` のレスポンス（スケジュール一覧等）に `Cache-Control` がなく、
  中間キャッシュ・ブラウザに残り得た。
- **修正**: `/api/*` に `Cache-Control: no-store` を付与。あわせて SW の
  キャッシュ名を `sleep-bgm-v2` に更新し古いシェルを破棄。

### 対応しないと判断した点（リスク受容）

- **HTTPS 化**: 自宅 LAN 内の HTTP 前提。必要ならリバースプロキシで TLS 終端する
  （README に VPN 推奨を明記）。トークンは平文 HTTP を流れるが、脅威モデル
  （自宅 LAN、家庭内の受動的盗聴者は想定外）では受容。
- **レート制限**: トークンは 128bit ランダムで総当たりは非現実的。
- **`api_rooms` のエラーメッセージ露出**: 内部例外文字列を返すが、認証必須化により
  閲覧者は所有者のみとなったため受容。

## 不具合所見

### B1（高）不正な timezone の保存でサーバが起動不能になる

- **場所**: `store.py` `update_settings` → `scheduler.py` `sync`
- **再現**: `PUT /api/settings {"timezone": "Mars/Olympus"}` → 保存は成功し、
  直後の `runner.sync()` の `CronTrigger(timezone=...)` で例外 → 500。
  さらに**次回 `serve` 起動時**も `ScheduleRunner.start()` → `sync()` で落ち、
  データファイルを手で直すまで起動不能。
- **修正**: `AppSettings.validate()`（`zoneinfo.ZoneInfo` で解決確認）を追加し、
  `update_settings` は**検証を通ってから**反映・保存。API は 400 を返す。
  メモリ・ファイルとも汚染されないことを回帰テストで担保。

### B2（高）1 リクエストがサーバ全体をブロック

- **場所**: `cli.py` `app.run(...)`、`sonos_client.py` `_apply_volume`
- **問題**: werkzeug の既定はシングルスレッドのため、フェードイン付き
  `play-now`（最大数十秒の同期 `time.sleep` ループ）の間、UI を含む
  全リクエストが応答不能になっていた。
- **修正**: `app.run(threaded=True)` に変更。さらにフェード処理自体を
  デーモンスレッドへ分離し、HTTP リクエストもスケジューラのジョブスレッドも
  即時に返るようにした（フェードは音量 0 から開始）。

### B3（中）数値フィールドの型未検証（500 と bool すり抜け）

- **場所**: `models.py` `Schedule.validate`
- **問題**: `volume: "loud"` のような文字列で比較演算が `TypeError` となり
  ハンドルされず 500。さらに JSON の `true` は Python では `bool`
  （`int` のサブクラス）のため `0 <= True <= 100` を**通過**し、
  意図しない値が保存され得た。
- **修正**: `_coerce_int` で int へ正規化（数値文字列は許容、`bool`・非数値は
  明確な日本語メッセージの `ValueError` → API では 400）。

### B4（低）SW キャッシュ版数の固定

- **場所**: `static/sw.js`
- **問題**: アプリシェル更新時にキャッシュ名が `v1` のままだと旧シェルが残る。
- **修正**: 今回のシェル変更に合わせ `v2` へ更新（S4 と同コミット）。
